# Listing management, media, and transfer formats

## Resource boundaries

Listings and integration descriptions are owner-managed resources. Listing deletion is archival, and restoration returns an archived listing to `draft`. Publishing is the explicit `draft -> published` command. Media metadata is owner-managed while its storage identity is immutable; deletion is a durable `deletion_pending -> deleted` workflow.

Wallet transactions, funding, purchases, checkouts, distributions, ledger entries, settlement, provider operations, payout history, referral attribution, and reversals are immutable or state-machine resources. Their APIs expose projections and explicit commands only—never generic financial `PATCH` or `DELETE`.

## Listing APIs and projections

- `POST /api/listings` creates a draft.
- `GET /api/listings` returns published public projections with `search`, `cursor`, and `limit`.
- `GET /api/me/listings` returns the authenticated owner's drafts, published, and archived listings; it additionally supports `state`.
- `PATCH /api/listings/{id}` is partial and cannot mutate lifecycle state.
- `POST /api/listings/{id}/publish`, `DELETE /api/listings/{id}`, and `POST /api/listings/{id}/restore` are lifecycle commands.

Public projections exclude `destination` and `external_key`. Owner projections include them. Both include ordered active media URLs and alt text.

## Listing media

`listing_capability.media` stores provider name, container/bucket, object key, detected MIME type, byte size, dimensions, deterministic position, alt text, and deletion state. Position `0` is the cover image. Public URLs are resolved at read time by the persisted provider identity, so changing the default affects only new uploads.

Uploads accept PNG, JPEG, GIF, and WebP up to 10 MiB. Content signatures and dimensions are inspected; filename extensions are not trusted. Object keys are generated by Cliqero. Filesystem storage rejects traversal and lives at a configurable absolute root outside source control.

Deletion first commits `deletion_pending`. The worker resolves the persisted provider, attempts remote deletion, and only then records `deleted`. Failures retain a safe error and remain discoverable for retry.

Configuration is in `config/modules/storage/listing-media.yaml`; copy the tracked example. Supported providers are `filesystem`, `supabase`, and `cloudflare-r2`. Supabase uses its Storage REST API and public bucket URL. R2 uses signed S3-compatible requests and a configured browser-facing bucket/custom-domain URL. Credentials never enter media records or API responses.

## Import/export

`POST /api/listings/import?format=json|csv|yaml&mode=create|upsert` and `GET /api/listings/export?format=json|csv|yaml` operate only on the authenticated owner's listings. Import accepts at most 1,000 records and 5 MiB per document. Results use HTTP 207 and contain totals plus per-record status, index, safe code, and message.

All formats represent: `id`, `external_key`, title, description, exact `price_minor`, ISO currency, destination, scalar metadata, lifecycle state, and ordered media `{url, alt_text, position}`. Create mode generates new IDs. Upsert requires an owner-scoped `external_key` or an existing ID owned by the caller; titles are never identity.

CSV columns are fixed in this order:

```text
id,external_key,title,description,price_minor,currency,destination,metadata,state,media
```

`metadata` and `media` are JSON encoded inside RFC-style quoted CSV cells. Export prefixes spreadsheet-formula-leading scalar cells (`=`, `+`, `-`, `@`) with an apostrophe, and Cliqero removes that protection when importing its own CSV.

YAML uses the core safe schema. Explicit tags, anchors, and aliases are rejected. JSON/YAML/CSV examples are in `docs/examples/`.

Remote media URLs are ingestion sources, not canonical storage identities. Only HTTP(S) is accepted. DNS is resolved before connecting and the selected public address is pinned for the request. Loopback, private, link-local, multicast, reserved, and documentation networks are rejected on every redirect. Downloads have a 10-second timeout, three-redirect limit, 10 MiB cap, image content-type requirement, and signature/dimension validation. User authentication headers are never forwarded.

Each record is isolated: a malformed or failed record does not roll back healthy records. A media failure is reported on that record; successfully stored media already has durable ownership and storage identity. Retrying safely uses upsert plus the owner-scoped external key. A future enhancement may add stricter gallery replacement semantics for upserted records.
