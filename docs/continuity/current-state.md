# Current State

Last audited: 2026-09-12. Branch: `ui`. Implementation audit boundary: `fda6ff9` plus the uncommitted repairs #1–#3 and the internal funding-integrity repairs. Always inspect current HEAD/code before relying on this snapshot.

Cliqero is a single-store, API-first catalogue platform. It is not an open multi-vendor marketplace and is not a Selar/Gumroad-style public seller platform. Catalogue participation is privileged: admin and accounts explicitly granted the appropriate catalogue/selling capability may list and sell within the single Cliqero store. Ordinary unprivileged accounts are buyers and may be promoters.

Single-store does not mean that only the platform can ever have seller economics. Where commercial policy assigns proceeds to an authorized seller, those earnings/settlement facts remain distinct from buyer wallet value, referral earnings, and platform treasury. Listing authorization and economic attribution should be explicit rather than inferred from marketplace assumptions or legacy field names.

The implemented commerce boundary is wallet-first:

`funding -> verified funding -> wallet credit -> available USD wallet -> wallet-only checkout -> purchase -> entitlement/access`

Referral distribution, authorized-seller accounting where applicable, and platform treasury are separate consequences of a paid purchase. Entitlement/access must not wait for distribution, seller settlement, or treasury processing.

- `POST /api/checkout` accepts only a listing ID and idempotency key. It snapshots a published USD listing, creates an awaiting-funds checkout, and spends available wallet balance only. It never invokes an external provider.

NOWPayments returns a payment address/amount/currency and optional asset/network metadata. Bank transfer supports multiple configured receiving accounts, each with country-only eligibility and ordered opaque `key`/`label`/`value` display fields. Optional country-currency mapping is separate from those filters. Cliqero does not interpret banking terminology. The authenticated account country determines every eligible receiving account; the customer selects one, its resolved collection currency is derived server-side, and initialization persists the selected account ID, opaque account snapshot, and rendered instructions in the funding record, so later configuration changes do not erase the original payment facts. It reports `awaiting_manual_confirmation`; no customer submission alone confirms funding. Finance-authorized operators can explicitly confirm a persisted `bank_transfer` funding record through `POST /api/operator/funding/{fundingId}/confirm-bank-transfer`; the state change and audit fact are committed together, and wallet credit remains a separate downstream processor.

The wallet overview keeps active funding concise and links to `/dashboard/wallet/funding?active=true`. Each active entry uses provider display metadata and opens only its own `/dashboard/wallet/fund?funding={id}` status page. Persisted funding status mode is exclusive from generic funding creation, shows indeterminate initialization progress with refresh, and does not render the generic amount/provider form. Cancellation is backed by migration `002_funding_cancellation.sql`; cancelled records remain auditable and do not create wallet credits.

The UI funding screen should consume `/api/wallet/funding-methods`, which filters enabled providers by authenticated account country; it does not require a user-selected currency for discovery. Provider preparation resolves collection/payment currencies. The development provider is registered through one server-side environment gate only in development/test runtimes, is marked `TEST ONLY` in local UI, and is absent from the production registry/API path; frontend hiding is not its security boundary. Checkout requests a server-calculated quote before checkout creation so the initial screen can show the available wallet balance and shortfall.

Funding preparation now keeps provider contracts explicit at the customer boundary: bank transfer applies a provider-level country filter before account-level filters, exposes only an eligible receiving-account selector and quote during preparation, and reveals the persisted account snapshot only after funding is created. All persisted funding status views identify the provider through `display_name` and expose the stable generic funding reference; bank status includes the explicit narration/reference instruction. Shared PostgreSQL exchange-rate caching uses a 24-hour default TTL (configurable with `EXCHANGE_RATE_CACHE_TTL_MS`) and retains exact conversion precision, while customer-facing rates are rounded to two decimals and omit the internal source name. Paystack hosted continuation is same-tab.

The canonical wallet-funding routes are `/dashboard/wallet/fund` for generic entry, `/dashboard/wallet/fund/{provider}?amount=...` for provider preparation, `/dashboard/wallet/fund?funding={id}` for persisted status/resume, and `/dashboard/wallet/funding` for paginated funding history. Legacy `/dashboard?section=wallet&item=fund` requests are server-redirected before hydration, preserving a safe `return` path and checkout `buy`/`checkout` context. The generic entry selects only canonical USD amount and an eligible provider; it performs no funding persistence or external initialization. Provider preparation owns optional collection/payment choices and the existing funding POST/initialization boundary; the current server quote uses provider-declared collection currencies, so Paystack resolves NGN while the wallet remains canonical USD. The wallet overview shows all active funding attempts through a server-side projection, while recent wallet activity is bounded to ten ledger entries. Initialized and awaiting payments can be resumed, verification-pending attempts show status only, and pending initialization/awaiting attempts can be locally cancelled without deleting or reversing value. Browser callbacks use `APP_URL` rather than the server bind address. Direct TRC20 verification uses the solidified TRON receipt and block height for confirmation counts. Bank-transfer instructions preserve line breaks, and customer evidence remains review-only. NOWPayments formats collection amounts from integer minor units, exposes state-specific progress and copy feedback, and omits ambiguous global asset/network metadata for multi-currency configurations.

In local Next.js development, the application container is retained across hot reloads through a global singleton. After changing a repository method's response shape, restart the web container so the live singleton cannot retain the previous contract; a fresh process and the current wallet API both use the array-shaped active-funding contract.

Funding history and cancellation are server contracts: `GET /api/wallet/funding` provides bounded, filtered, cursor-based funding attempts; `GET /api/wallet/transactions` remains bounded wallet activity; and `POST /api/wallet/fund/{id}/cancel` transitions only `initialization_pending` or `awaiting_payment` to `cancelled`, records an audit fact where supported, and does not pretend to cancel a remote provider payment. Late provider work cannot initialize or verify a locally cancelled record. Environments created from the original schema must apply the repository migration that adds the `cancelled` state before enabling this action.
